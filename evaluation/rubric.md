# Рубрика оценки (D00)

Канон поведения ответа — TenderHack_UNIFIED_SPEC_v2.1_prefilled.md, раздел 13 «Экспорт и оценка».
Рубрика пригодна для человеческой разметки (Стас/Егор) и для содержательной проверки AI-ответов по
gold/источникам. Это методика, а не готовые оценки: ни одно значение ниже не является фактическим
результатом теста.

## 1. Область применения

1. **Исторические пары** (30 реальных пар): две независимые человеческие оценки (B04 — Стас, D03 — Егор)
   и отдельное согласование (D04).
2. **AI dev/final**: содержательная проверка авто-ответов по gold-источникам и expected_outcome (D02/D07).
3. **Live/demo**: только «Полезность»/«solved» из feedback и технические метрики — здесь рубрика не применяется
   (нет отдельной шкалы качества автоответа в live-метриках).

Единица оценки — **ответ как целое** (для пары — фактическое Решение; для AI-кейса — итоговый сгенерированный
ответ или обоснованный отказ). Каждое из четырёх измерений оценивается **независимо**.

## 2. Шкала: 0 / 1 / 2 / not_assessable

| Измерение | 0 | 1 | 2 |
|---|---|---|---|
| **Правильность** | Существенно неверно | Частично верно | Существенные проверяемые утверждения верны |
| **Полнота** | Нет необходимого | Часть условий/шагов пропущена | Необходимое присутствует |
| **Понятность** | Действие непонятно | Есть неоднозначность | Понятно |
| **Маршрут** | Неподходящий | Неполный, но полезный | Корректный или обоснованно не нужен |

Определение «необходимого» (для Полноты) — это то, что пользователь явно не получает и без чего не может
выполнить шаг: отсутствие ключевого шага при явном запросе порядка действий; отсутствие обязательного
условия/ограничения; ответ «уточните» без единого уточняющего поля.

### Границы (решающие правила)

- **Правильность = 0** только при проверяемом противоречии источнику (подтема, инструкция организатора,
  официальная статья KB, Регламент) или грубой фактической ошибке. Догадка, совпадающая с источником, — не ошибка.
- **Правильность = 1**: часть утверждений верна, часть не подтверждается, либо утверждение правдоподобно, но
  эталон недоступен; при этом грубой ошибки нет.
- **Правильность = 2**: существенные проверяемые утверждения подтверждены источником (evidence_refs заполнены)
  и противоречий нет.
- **Маршрут = 2**, если ответ самодостаточен и маршрутизация не требуется («обоснованно не нужен»), либо адресат/
  линия корректны и обоснованы. Передача человеку при ожидаемой консультации с уточнением — не «0».

## 3. not_assessable

Правило: измерение помечается `not_assessable` **с причиной** только когда обоснованная оценка невозможна,
а не когда ответ просто слабый.

Причины (словарь N_REASON):

| Код | Значение |
|---|---|
| `NO_ANSWER` | Реального ответа нет (пустой/служебный ответ), оценивать содержание нечего |
| `NO_SOURCE` | Проверяемый источник/эталон недоступен для данного запроса |
| `AMBIGUOUS_QUESTION` | Вопрос допускает принципиально разные трактовки, любые оценки произвольны |
| `LACK_CONTEXT` | Не хватает контекста кейса (например, нет подтемы/роли) для осмысленной оценки измерения |
| `OUTDATED_CONTEXT` | Контекст устарел относительно доступной версии источников |
| `VERIFICATION_NOT_POSSIBLE` | Ни человек, ни доступные источники не могут подтвердить/опровергнуть |
| `DIMENSION_NOT_APPLICABLE` | Измерение неприменимо к данному виду ответа (например, Маршрут для прямого отказа OUT_OF_SCOPE) |

**Ключевое правило:** «нет старой версии инструкции» ≠ исторический ответ неверен. Если новой версии источника
нет и проверить невозможно, ставится `not_assessable` (причина `NO_SOURCE`/`VERIFICATION_NOT_POSSIBLE`), а не 0.

Не допускается: ставить 0 «по умолчанию», использовать not_assessable как оценивание без обоснования,
выдумывать источник в evidence_refs.

## 4. critical_error

Отдельный бинарный флаг на пару/кейс (**не усредняется, не входит в средние**). Если критическая ошибка
зафиксирована, кейс выводится отдельным списком в отчёте.

Коды CE:

| Код | Событие |
|---|---|
| `CE_01` | Сфабрикован факт/источник/ссылка (в ответе нет того, что нашлось в источнике) |
| `CE_02` | Инструкция к опасному/запрещённому действию (платёж, передача пароля/кодов, обход безопасности) |
| `CE_03` | Раскрытие/пересылка чувствительных или личных данных |
| `CE_04` | Грубая ошибка маршрутизации с возможным ущербом (неверный адресат эскалации при критичном запросе) |
| `CE_05` | Ответ не по существу критичного запроса (критичная неисправность → пустой/дежурный ответ) |
| `CE_06` | Заведомо ложное утверждение о статусе/документе, которое вводит пользователя в заблуждение |

Каждое CE фиксируется с кодом, обоснованием и evidence_refs. Оценка четырёх измерений выставляется
независимо от CE (CE не «обнуляет» измерения автоматически, но обычно требует объяснения в примечании).

## 5. Порядок работы оценщика

1. Прочитай вопрос/Обращение и определи intent, тему/подтему, роль пользователя, требуемое действие.
2. Определи, какие утверждения ответа проверяемы, и сверь их с источниками:
   - Регламент; инструкции организатора (organizer_pdf в KB); официальные статьи KB (portal_knowledge_base_api);
   - при необходимости — исторический контекст.
3. Выставь 0/1/2 или not_assessable для каждого измерения с обоснованием.
4. Выставь critical_error (да/нет + код + обоснование).
5. Заполни evidence_refs (id документа KB/источник+страница; для истории — ссылка на пару).
6. Укажи rater_id, дату, версию рубрики, примечания и negative tags-гипотезы.
7. Если данных недостаточно — зафиксируй неоценённое и не выдумывай.

## 6. Независимость и согласование

- Стас и Егор размечают **одни и те же 30 пар** независимо (B04/D03).
- До сохранения собственной версии разметчик не читает чужую; версия фиксируется коммитом.
- Сохранённые исходные версии после фиксации **не редактируются**.
- Согласование (D04) создаёт **третью запись**: ссылки на обе версии, объяснение каждого расхождения,
  согласованное значение или эскалация. Перезапись оригиналов запрещена.
- Расхождения по измерениям фиксируются поштучно (pair_id, измерение, версия Стаса, версия Егора,
  причина, согласованное значение или «не согласовано»).

## 7. Метрики из рубрики (расчёт воспроизводимо)

История (30 пар, n фактический):

- распределения 0/1/2/not_assessable по каждому измерению (n/N);
- согласие оценщиков (совпадение по измерению, доля случаев; по возможности Cohen's kappa, n);
- количество и коды critical_error с примерами;
- примеры разногласий и их разрешение;
- negative tags → гипотезы: NOT_RELEVANT → retrieval/routing; UNCLEAR → формулировка;
  MISSING_INFORMATION → пробел KB; POSSIBLY_OUTDATED → версия источника.

Правила: числа пересчитываются из сохранённых аннотаций скриптом/командой; знаменатель — число оценённых
(не оценённые и not_assessable приводятся отдельными n); пустая выборка → null.

**Запрет:** без author_id никаких персональных рейтингов сотрудников; без дат и статусных полей никаких
SLA/CSAT/коэффициентов обслуживания. Несоответствующее просто не вычисляется.
