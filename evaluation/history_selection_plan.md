Основание: v2.1, раздел 13 (История) — 30 реальных пар, две независимые человеческие оценки,
до 10 учебных примеров вне итоговых 30.

**Вывод по истории:** реальные пары «вопрос (Описание) → ответ (Решение)» доступны и достаточны по объёму
для выборки 30 пар. Между записью и ответом — одна строка без message sequence.

**Вывод по авторам:** в выгрузке **нет** identifier оператора/исполнителя, таймстампов, линии/адресата,
сла/CSAT-полей. Значит:

- `author_id` для истории = **null/unknown** всегда;
- персональный рейтинг сотрудников, SLA и CSAT **не вычислимы и не выдумываются**;
- временная сегментация (окна, п95 ответа) невозможна;
- оценка истории — только содержательная (рубрика), без сервисных KPI.

## 2. Пара «истории»

Каждая паря состоит из:

- `Описание` — текст обращения (в 23 508 строках содержит префикс `Подтема запроса: <подтема>/<текст>`);
- `Решение` — фактический ответ службы поддержки.

При построении пары в D01 префикс «Подтема запроса:» **выносится в отдельное поле** `subtopic_raw`,
а текст запроса очищается от префикса. «Решение» — предмет оценки, не gold.

## 3. Правила отбора 30 пар (применяются в D01)

1. **Действительность пары**: `Описание ≥ 25 символов`, `Решение ≥ 40 символов` после очистки;
   пустые и служебные записи исключаются. Допускаются короткие шаблонные ответы, если они реально
   составляют типовую картину (например, «Проблема устранена <ссылка>»), но их доля в выборке ограничена.
2. **Дедупликация**: удалить точные дубли (Описание, Решение); близкие перефразировки группируются
   в group_id, из группы в выборку попадает одна пара (парафраз не «протекает» между dev/final/history).
3. **Стратификация по подтемам**: по частоте значения из «Подтема запроса:» выбираются ≥ 5–8 ведущих
   подтем (ожидаемо: УПД/исполнения, ЭП/сертификаты, регистрация/ЛК, контракты/оферты и т.п.). «Тема»
   как сырое поле — только вторичный признак из-за шума (795 значений).
4. **Разнообразие типа ответа**: включаются и инструктивные ответы («создайте новое исполнение…»),
   и маршрутизирующие («обратитесь в поддержку ЕИС…»), и статусные («проведены работы»), чтобы не
   создавать перекос в «хорошие» ответы.
5. **Обезличивание**: в аннотации и материалы не попадают ФИО, номера контрактов/закупок, ссылки на
   конкретные обращения и персональные данные; в манифесте — только pair_id, row reference и хэши.
6. **Резерв**: выбрать 30 основных + до 10 резервных пар (на случай `not_assessable` → замена с фиксацией).
7. **Единственный список pair_id** для обоих разметчиков (B04/D03) — одна и та же выдача, один порядок.
8. **Честность**: если по правилам не набирается 30 подходящих пар — фиксируется фактическое n и blocker,
   пустой набор не заполняется синтетикой.

## 4. pair_id схема (единая для B04/D03)

- `HIST-0001` … `HIST-0030`; резерв `HIST-R01` … `HIST-R10`.
- `evaluation/history/pairs_manifest.json` (D01):
  - `file` — путь и SHA-256 исходной выгрузки;
  - `pair_id`, `row_index` (0-based позиция строки в листе без заголовка), `content_hashes`
    (sha256(Описание), sha256(Решение)), `topic_raw`, `subtopic_raw`, `pair_status` (selected/reserve),
    `notes_null` (признак not_assessable-рисков).
- Манифест фиксируется commit'ом до начала разметки; пары не пересортировываются.

## 5. Отражение ограничений

- Подтема из строки запроса — неканоническая таксономия; сверять с `НН 2026/Темы_подтемы_обращений.xlsx`
  (88 строк: №/Тема/Подтема; SHA-256 `f5649e083b5f0c13cf346e26387064aca2c33edb9c9e7ceee1c3cc4641f5d05a`).
- Нет дат → нельзя ранжировать пары во времени, окно «2026» однородно.
- Ответы могут ссылаться на события позже KB snapshot (пример: строка 5б в УПД) — такие пары
  помечаются с `OUTDATED_CONTEXT`/`VERIFICATION_NOT_POSSIBLE` по рубрике, но включаются как реальный случай.
- Аннотации и манифест не содержат личных данных (требование «материалы разметки обезличиваются»).

## 6. Зависимости

- Правила применяются в **D01** (реальный отбор пар). D00 фиксирует только методику.
- Вход для отбора: реальная выгрузка (`НН 2026/Выгрузка СТП за 2026.xlsx`), таксономия
  (`НН 2026/Темы_подтемы_обращений.xlsx`).
- Блокер для полного среза: отсутствие во входных данных дат/авторов/линий не мешает отбору пар,
  но исключает SLA/CSAT/персональные метрики (зафиксировать в D01-reports).
